# Синтетическая оценка обзоров: synthetic-ru-v1

Добавлен явный [диагностический профиль qwen3:14b-q4_K_M](../docs/qwen3-14b-profile.md), только development/think-false. По умолчанию остаётся qwen3-8b. `--check-profile` явно разрешает metadata/render-only без генерации; `--probe` выбирает только dev-01. Обычный план по-прежнему не использует сеть.

20 новых искусственных русскоязычных переписок, не данные пользователей. `inputs/` содержит только запросы существующего API. В `annotations/` — отдельная ручная разметка ожидаемых вопросов, обязательных источников, существенных фактов, допустимых статусов, срока/null, needs_context и недопустимых выводов. **Разметка не передаётся модели**: batch-loader читает только manifest и inputs, не открывает annotations и таблицу оценки. Дословное совпадение текста не требуется.

10 development (`dev-01`…`dev-10`) разрешены для настройки. 10 holdout (`hol-01`…`hol-10`) предназначены только для итоговой оценки после фиксации модели, промпта и параметров. В этом изменении промпты не настраивались и генерации на реальной модели не выполнялись. Holdout создан тем же автором и по тому же заданию: это разделённая синтетическая проверка, **не независимая оценка реальных клиентов**. Позже нужно добавить обезличенные реальные переписки с отдельной разметкой и разрешённым использованием. После использования holdout для настройки он перестаёт быть holdout; нужен новый замороженный набор.

Разметка — предложение человеческого эталона, а не доказанный единственный ответ. required_source_ids — обязательные основания вывода; дополнительные релевантные ID допустимы. allowed_statuses можно расширить после независимого обсуждения неоднозначности, зафиксировав новую версию разметки. essential_facts проверяются по смыслу. «Клиент получил» допустимо как атрибуция его слов; независимое наличие/содержимое файла не выдумывается. ## Batch-команда

Использует существующий диагностический Runner, рабочие morning-v3/topics-v1, один вызов на клиента. API и промпты не меняет. По умолчанию — development, think=false, план без сети. Ни автоматических повторов, ни repair, ни скрытой обрезки. Входы выбранной части сначала проверяются по API-ограничениям. Бюджет и совместимость проверяются для каждого вызова отдельно; preflight-ошибка останавливает batch. После ошибки уже начатой генерации переход к следующему примеру разрешён без повтора предыдущего; exit остаётся ненулевым.

| Режим | Шаблон | Sampling | Контекст / резерв | Timeout |
|---|---|---|---|---|
| think-false | проверенный /no_think, пустой think-блок | temperature=0, остальные прежние defaults Ollama | 8192 / 1500 | 120s |
| think-true | проверенный /think, без пустого блока | temperature=0.6, top_p=0.95, top_k=20, min_p=0 | 8192 / 4096, включая thinking | 180s |

Оба режима: qwen3:8b, stream=false, keep_alive=30m, shift=false, truncate=false. Проверки checksum/digest/Ollama 0.40.5/хеша шаблона/render-only сохранены. В thinking проверяется format=schema в helper, затем точный payload в транспорте; в false — прежняя helper-проверка и точный format=schema payload в транспорте. Отсутствие rendered_template или несовпадение — отказ без обхода. Смена think меняет также sampling, резерв и timeout: результаты не изолируют влияние think.

После [установки отдельного helper-окружения и ресурсов](../tools/context_budget/README.md), из корня проекта:

```powershell
$env:BRIEFING_BUDGET_PYTHON=(Join-Path $PWD '.venv-budget/Scripts/python.exe')
$env:OLLAMA_MODEL='qwen3:8b'
go build -o bin/evaluate-batch.exe ./cmd/evaluate-batch
./bin/evaluate-batch.exe
./bin/evaluate-batch.exe --split development --mode think-true
```

Эти команды только строят планы. API-токен не нужен. В GoLand: Go Build, Package `finkoper-morning-briefing/cmd/evaluate-batch`, Working directory — корень; те же env, Program arguments например `--split development --mode think-true`.

Реальные вызовы разрешает **только ручной** `--run`. Ниже примеры команд оператора, в этой работе они на реальной Ollama не запускались:

```powershell
./bin/evaluate-batch.exe --split development --mode think-false --run --out evaluation/reports/dev-false.jsonl
./bin/evaluate-batch.exe --split development --mode think-true --run --out evaluation/reports/dev-true.jsonl
# Только после фиксации конфигурации и завершения настройки:
./bin/evaluate-batch.exe --split holdout --mode think-false --run --out evaluation/reports/holdout-false.jsonl
./bin/evaluate-batch.exe --split holdout --mode think-true --run --out evaluation/reports/holdout-true.jsonl
```

Каждая команда делает максимум 10 последовательных генераций; модели не передаются соседние примеры или их разметка. Без --out при --run создаётся новый timestamp-файл в evaluation/reports. Существующий файл никогда не перезаписывается. Без --run вывод — stdout, --out позволяет сохранить план. Каталог reports и JSONL исключены из Git; заполненную ручную таблицу также храните внутри reports. На Unix файлы создаются с 0600 (Windows использует ACL окружения).

Для ручного Linux-запуска соберите `go build -o bin/evaluate-batch ./cmd/evaluate-batch` с GOOS=linux GOARCH=amd64 CGO_ENABLED=0 и разместите бинарник/исходные inputs/manifest вручную. Используйте отдельное venv, resources и loopback Ollama с путями из [инструкции диагностики](../docs/thinking-diagnostics.md). Например **план** на сервере, без загрузки API-конфига и токена:

```bash
cd /opt/finkoper-morning-briefing/current
sudo -u finkoper-briefing env \
 BRIEFING_BUDGET_PYTHON=/opt/finkoper-morning-briefing/venv-budget/bin/python \
 BRIEFING_BUDGET_HELPER="$PWD/tools/context_budget/helper.py" \
 BRIEFING_TOKENIZER_DIR=/opt/finkoper-morning-briefing/resources/tokenizer/qwen3-8b \
 BRIEFING_BUDGET_TIMEOUT=60s \
 OLLAMA_MODEL=qwen3:8b OLLAMA_BASE_URL=http://127.0.0.1:11434 \
 ./evaluate-batch --split development --mode think-false
```

Для генераций оператор отдельно добавляет --run и --out с новым абсолютным путём в доступном ему каталоге; каталог отчётов release может быть недоступен finkoper-briefing. Сервис, БД и systemd не нужны. Команда ограничивает только собственные запросы, не общую GPU.

## Отчёты и ручная оценка

На пример сохраняются example_id/split, dataset_version и manifest hash, hash исходного файла и сериализованного user, prompt_version/hash, schema_version/format hash, модель, ожидаемый digest и tokenizer manifest hash. model_digest остаётся null в плане; при успешной проверке закреплённого digest заполняется подтверждённым значением. Поля mode=plan/run и thinking_mode различаются. Сохраняются параметры, timeout, хеш запроса/рендера, подтверждение совместимости, бюджет, финальный JSON, ошибки структуры/транспорта, токены и длительности helper/compatibility/render/HTTP/Ollama/pipeline, число генераций и время записи.

message.thinking не печатается и не сохраняется: только наличие и UTF-8 размер. Невалидный raw content скрыт, result=null при ошибках. Length/not done/невалидный JSON не считаются успехом. Полный структурно корректный JSON не означает смысловую точность.

Скопируйте [manual-review.csv](manual-review.csv) в evaluation/reports и заполните отдельную копию для каждого отчёта. Один и тот же рецензент сверяет вход, разметку и результат по смыслу, сопоставляя темы; полезна вторая независимая проверка спорных мест. Пустая ячейка — **не оценено**, 0 — оценено, ошибок нет. Значения — целые числа; notes содержит ID тем/сообщений и объяснения.

| Колонка | Что считать вручную |
|---|---|
| missing_questions / extra_questions | Пропущенные ожидаемые / лишние самостоятельные вопросы |
| wrong_merges / duplicates | Неверные объединения разных вопросов / повтор одной темы |
| lost_essential_facts | Утерянные существенные факты, включая суммы, даты и обещания |
| invented_facts / invented_actions | Выдуманные сведения / незапрошенные действия |
| wrong_deadlines / wrong_statuses | Ошибочные сроки (включая лишние) / статусы сопоставленных тем |
| needs_context_errors | Неверный флаг необходимости контекста |
| source_errors | Потерянные обязательные или лишние нерелевантные основания вывода |
| reference_disputes | Неоднозначности/ошибки самой разметки; описать отдельно |

Если тема пропущена, считайте её в missing_questions, а не автоматически дублируйте все ошибки её полей. Для объединения отметьте wrong_merges, в notes перечислите затронутые вопросы; другие реально потерянные факты отметьте отдельно. До сравнения согласуйте этот порядок. Сводите число проверенных примеров и ошибок по каждой категории, отдельно development/holdout и режимы; не превращайте необоснованную сумму в «процент качества». Сопоставляйте одинаковые ID попарно и сохраняйте спорные решения.

Автоматические проверки ограничены API-входами, бюджетом, совместимостью, JSON/типами/enum, существованием ID и наличием period-источника, done/length. Они не устанавливают релевантность источников, правильное число тем, полноту фактов, сроки и статусы по смыслу. Совпадение ключевых слов не оценивается. Mock-тесты доказывают работу инструмента, а не качество модели.

## Будущая более сильная модель

Сначала зафиксируйте текущие результаты, digest, prompt/schema hashes, набор и разметку. Модели инструмент не устанавливает. Для ещё не подтверждённых моделей отдельно подготовьте и проверьте локальный токенизатор (включая normalization), chat template, специальные токены, digest/версию runtime, точный render-only и соответствие prompt_eval_count; установите обоснованные контекст и резерв. Поддержка нового профиля требует явного изменения и тестов; команда принимает только явно зарегистрированные профили (8B и отдельный первоначальный 14B). Не переименовывайте manifest и не отключайте защиту ради запуска.

После подтверждения профиля сначала проверяйте development. Заморозьте конфигурацию, затем один итоговый прогон holdout; сравнивайте одинаковые входы и правила ручной разметки. Различия sampling, reasoning, резервов, времени и стоимости указывайте рядом с качеством. Holdout не используйте для очередного улучшения промпта под видом независимого теста.
