# Утренний обзор FinKoper

Отдельный Go-сервис: HTTP → устойчивая очередь SQLite → один worker → Ollama → проверенный JSON в SQLite. Без расписания, frontend, отправки сообщений и создания задач. Весь период одного клиента поступает одним запросом; ночной подготовки нет. Существующие тональность, RAG и Ollama не изменяются.

Один worker ограничивает **только этот сервис**. Запросами тональности и RAG к общей GPU он не управляет. Они могут конкурировать за RTX 3060, менять задержки и вызывать загрузку модели. Причина наблюдавшейся перезагрузки обработчика не установлена; глобальные настройки Ollama сервис не меняет. Скорость 54 токена/с — исходное измерение пользователя, не гарантия времени обработки.

## Локальный запуск (PowerShell / терминал GoLand)

Нужен Go **1.27.1** (версия в go.mod). `modernc.org/sqlite` и `gofrs/flock` закреплены в go.mod/go.sum; CGO не нужен. Из корня проекта:

```powershell
$env:CGO_ENABLED='0'
go test ./...
go vet ./...
go build -o bin/briefing.exe ./cmd/briefing
```

В отдельном терминале пользователь может открыть SSH-туннель (он не запускался автоматически):

```text
ssh -N -L 11435:127.0.0.1:11434 user85037@193.106.173.205
```

В терминале приложения:

```powershell
$env:BRIEFING_LISTEN_ADDR='127.0.0.1:18084'
$env:BRIEFING_DB_PATH='data/briefing.db'
# Создаёт новый локальный токен без записи в репозиторий.
$env:BRIEFING_API_TOKEN=[Guid]::NewGuid().ToString('N') + [Guid]::NewGuid().ToString('N')
$env:OLLAMA_BASE_URL='http://127.0.0.1:11435'
$env:OLLAMA_MODEL='qwen3:8b'
$env:OLLAMA_TIMEOUT='120s'
go run ./cmd/briefing
# Или после сборки: .\bin\briefing.exe
```

В GoLand: Go Build configuration, Run kind = Package, Package path = `finkoper-morning-briefing/cmd/briefing`, Working directory = корень проекта; задать эти шесть переменных в Environment. Токен задаётся локально, конфигурацию с секретом не сохранять как shared. Приложение само `.env` не читает; `.env.example` — шаблон переменных.

Умолчания: `127.0.0.1:18084`, `data/briefing.db`, `http://127.0.0.1:11434`, `qwen3:8b`, `120s`. `BRIEFING_API_TOKEN` обязателен; без него запуск прекращается. `OLLAMA_TIMEOUT` — положительная Go duration на один HTTP-вызов. Ollama не открывать в интернет.

Остановка — Ctrl+C или SIGTERM. Сервис прекращает приём HTTP, отменяет активный вызов, дожидается worker и закрывает БД. Незавершённый `running` возвращается в `queued` при следующем запуске. После аварии обработка может повториться: **exactly-once не обещается**. При обычных ошибках Ollama задание становится `failed`, автоматических повторов генерации нет. Ошибка сохранения останавливает процесс, чтобы не продолжать работу с потерянным результатом.

## API

Контракт: [OpenAPI](postman/specs/briefing.openapi.json). Обязательный Bearer-токен у всех рабочих API; `GET /healthz` публичный, проверяет приложение и SQLite, не вызывает модель и возвращает только `{"status":"ok"}`. При недоступной БД — 503.

Общий токен удостоверяет доверенный backend FinKoper. `company_id` — переданный им tenant scope, **не доказательство прав конечного пользователя**. Проверка прав сотрудников и фильтрация каналов остаются обязанностью FinKoper. Это server-to-server API, браузерная интеграция и CORS не предусмотрены.

Создание (PowerShell, токен должен быть задан в этом же терминале):

```powershell
curl.exe -sS http://127.0.0.1:18084/healthz
curl.exe -sS -X POST http://127.0.0.1:18084/v1/briefings `
  -H "Authorization: Bearer $env:BRIEFING_API_TOKEN" `
  -H 'Content-Type: application/json' -H 'Idempotency-Key: example-01-v1' `
  --data-binary '@examples/01.json'
```

HTTP 202: `{"job_id":"...","status":"queued","created_at":"..."}`. При повторе статус может быть уже `running`, `succeeded` или `failed`. Уникальность ключа — `(company_id, Idempotency-Key)`. Нормализуются порядок JSON-полей, форматирование, даты через Go time и отсутствие/null/[] контекста. Порядок элементов массивов и содержимое строк значимы. Даже при заполненной очереди повтор принятого задания возвращается; другое содержимое с тем же ключом — 409. Ключи и результаты сохраняются без TTL.

```powershell
$jobId='ВСТАВЬТЕ_JOB_ID'
curl.exe -sS "http://127.0.0.1:18084/v1/briefings/${jobId}?company_id=company_1" `
  -H "Authorization: Bearer $env:BRIEFING_API_TOKEN"
```

Поиск всегда по `(company_id, job_id)`; чужая компания получает 404. Ответ содержит `job_id`, `status`, `created_at`, `prompt_version`, `schema_version`, `result`, `error`, `metrics`. `result` — объект `topics` только при успехе; иначе null. `error` — безопасный код, без сырого ответа модели. Статусы: queued/running/succeeded/failed. При `failed` backend решает, нужен ли новый запрос с новым ключом.

Ошибки: 400 — JSON/валидация/отсутствующий ключ или company_id; 401 — токен; 409 — конфликт ключа; 413 — HTTP body; 422 — бюджет модели; 429 + `Retry-After: 5` — очередь; 500 — хранилище. Очередь ограничена 100 **незавершёнными** заданиями (queued + running). Готовые результаты не входят в этот лимит. Размер хранилища растёт: политику хранения и удаления для production нужно определить отдельно.

## Валидация и модель

Вход не обрезается. Body ≤ 1 MiB; максимум 200 сообщений суммарно с контекстом; text непустой, ≤ 16000 UTF-8 байт; строковые ID непустые, ≤128 байт. Уникальность message ID проверяется между обоими массивами. Только роли client/staff и каналы email/max/telegram/finchat. Даты RFC3339 с часовым поясом; from < to; messages внутри [from,to), context_messages строго до from. Перед моделью каждый массив отдельно стабильно сортируется по времени: равные времена сохраняют исходный порядок. В user JSON контекст и период явно размечены разными полями.

Отдельная **консервативная оценка, не точный токенизатор**: число UTF-8 байт системного промпта + сериализованного отсортированного user JSON + 512 условных токенов на шаблон + 1500 резерв ответа ≤8192. Для byte-level BPE это намеренно жёсткая оценка; для других токенизаторов/шаблонов строгой математической гарантии нет. Она отклонит часть входов, которые фактически поместились бы в контекст. Body limit не является лимитом контекста модели. При смене модели нужно заново проверить совместимость бюджета. JSON schema передаётся как `format`, а не добавляется текстом в промпт.

Вызов native `POST /api/chat`: model=qwen3:8b (настраивается), stream=false, think=false, keep_alive=30m, temperature=0, num_ctx=8192, num_predict=1500, `format`=JSON Schema, `truncate=false`. Последний параметр присутствует в [актуальном контракте Ollama](https://github.com/ollama/ollama/blob/main/api/types.go); [chat handler](https://github.com/ollama/ollama/blob/main/server/routes.go) передаёт его в подготовку контекста. Версия установленной серверной Ollama **не проверялась**. Старые версии могут игнорировать поле; сервис не считает его подтверждением отсутствия обрезки и всегда применяет свой бюджет. Перед production необходимо проверить установленную версию, поддержку structured outputs/think/truncate и поведение на границе контекста. Нестандартных endpoint для токенизации или probing с генерацией нет.

Промпт и схема находятся в `internal/briefing/prompt.go`, версии `morning-v1` и `topics-v1` сохраняются с каждым заданием. При изменении текста повышайте версии; queued задания неизвестной версии завершаются `unsupported_job_version`, а не выполняются другим промптом. Модель получает правила против инструкций из переписок; это снижает, но не устраняет риск prompt injection и смысловых ошибок.

Независимая проверка ответа: JSON без лишних полей, все обязательные поля и типы, enum статуса, непустой text, nullable deadline, существующие уникальные источники и минимум один источник из messages у каждой темы. Для resolved срок обязан быть null. Требуются `done=true` и `done_reason=stop`; length — ошибка. HTTP-ошибки, поле error, таймаут и невалидный JSON → failed. Сырой ответ не выдаётся и не сохраняется как успешная сводка. Структурная проверка **не доказывает смысловую точность**, полноту тем и корректность привязки сроков.

## Надёжность и данные

SQLite WAL, synchronous=FULL, одна SQL connection, короткие транзакции при приёме/выборе задания. Во время генерации транзакция не открыта. Уникальный индекс company+key и локальная сериализация приёма обеспечивают одновременные одинаковые запросы. FIFO по порядку записи. Файловая OS-блокировка `<db>.lock` удерживается весь процесс и снимается ОС после аварии; второй процесс для того же файла прекращает запуск. Используйте один канонический путь на локальном диске, без hardlink, сетевых ФС и разных mount-алиасов одного файла. Symlink самой БД запрещён. Горизонтальное масштабирование не поддерживается.

БД содержит переписки и результаты в открытом виде. Ограничьте доступ к каталогу средствами ОС; резервное копирование делать SQLite-aware либо после остановки сервиса (учитывать WAL). API-токены не пишутся в БД/логи. Логи содержат события, job_id, статусы и длительности, без текстов сообщений и ответов Ollama.

Метрики отдельно в `metrics`: queue_wait_ms, processing_ms, ollama_total_ms, ollama_load_ms, prompt_eval_ms, generation_ms, input_tokens, output_tokens. Отсутствие — null, полученный 0 — число 0. Длительности Ollama переводятся из наносекунд в миллисекунды; processing_ms измеряется приложением, queue_wait_ms — от создания до начала текущей попытки (включает простой после перезапуска). При ошибке сохраняются доступные метрики; после аварии метрики прерванной попытки не гарантируются. Ожидающая/прерванная работа имеет null до завершения.

## Проверки и ручная оценка

```powershell
gofmt -w cmd internal
go test ./...
go vet ./...
$env:CGO_ENABLED='0'
go build -o bin/briefing.exe ./cmd/briefing
go build -o bin/evaluate.exe ./cmd/evaluate
```

Обычные тесты используют httptest HTTP mock Ollama и временную SQLite, к AI-серверу не обращаются. Они проверяют auth, контекст, гонку идемпотентности/конфликт, tenant isolation, переполнение очереди, блокировку второго экземпляра, восстановление, один активный вызов, ошибки модели, ссылки, бюджет и размер body.

Ручная команда **действительно вызывает Ollama**, один вызов на файл, без повторов и эталонной подстановки; запускается пользователем при открытом туннеле:

```powershell
$env:OLLAMA_BASE_URL='http://127.0.0.1:11435'
go run ./cmd/evaluate examples/01.json examples/02.json
```

Проверьте самостоятельно:

* `01.json`: шесть тем; комплектность awaiting_staff без срока; акт Вектора awaiting_client; зарплата awaiting_staff со сроком «завтра до 11:00»; требование awaiting_client до скана; сверка resolved; отпуск needs_context=true. Срок зарплаты не относится к комплектности.
* `02.json`: две темы; отпуск awaiting_staff, needs_context=false, согласованный порядок (заявление+приказ, расчёт у кадровика) и обещание сотрудника без заявления о выполнении; акт resolved с подтверждением клиента из другого канала. Смену банка не включать.

Эталоны описаны только для ручного сравнения; код не заменяет ими ответ. Качество qwen3:8b и реальные времена на GPU пока не проверены.

Postman локальные артефакты и дополнительный прогон описаны в [postman/README.md](postman/README.md). Использован skill [postman:api-engineer](postman/skills/api-engineer/SKILL.md). Облачная workspace не создавалась, ничего не публиковалось.

## Будущий запуск на сервере

[deploy/briefing.service](deploy/briefing.service) — только пример, **не установлен**. Для него отдельно подготовить пользователя, бинарник `/opt/finkoper-briefing/briefing`, каталог `/var/lib/finkoper-briefing`, env-файл `/etc/finkoper-briefing.env` с правами 0600. В env задать DB_PATH=/var/lib/finkoper-briefing/briefing.db, listen=127.0.0.1:18084, OLLAMA_BASE_URL=http://127.0.0.1:11434 и секрет. Linux-сборка из PowerShell:

```powershell
$env:GOOS='linux'; $env:GOARCH='amd64'; $env:CGO_ENABLED='0'
go build -o bin/briefing-linux-amd64 ./cmd/briefing
Remove-Item Env:GOOS, Env:GOARCH
```

Unit не меняет Ollama, Nginx или firewall. Развёртывание, подключение к серверу и изменение инфраструктуры автоматически не выполняются.
