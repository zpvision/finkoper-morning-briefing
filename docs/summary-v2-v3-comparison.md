# Локальная summary-диагностика: v2 против v3

Рабочие API, morning-v3, topics-v1 и задания остаются прежними. Переход на внешний API не выполняется. Документация интеграции рабочего сервиса не переключается на summary: сначала нужны реальные ответы диагностического v3.

`diagnostic-summary-v3` переписан целиком, а не дополнен хвостом запретов. Он организован вокруг содержания обращений, типа высказывания, актуального состояния просьбы, связанного контекста и оснований сводки. Короткие искусственные примеры различают сообщение о действии, просьбу, намерение и обещание; в них нет имён, сумм или ID набора. Порядок «как раньше» раскрывается с ограничениями/исключениями либо прямо отмечается отсутствие его деталей. Самостоятельные старые темы не переносятся в обзор. Снятые сроки не действуют; напоминание не создаёт новую просьбу. Источники выбираются по утверждениям, включая использованный контекст, а не по общему «да/спасибо» и не копированием всех ID. Цитируемые модельные инструкции остаются данными.

V2 сохранён побайтно в SummaryPromptV2, SHA-256 `8cc6dc4d3fad8eba8da327ecf9837aaa0213c6f978678e65c4ad105464d8ff31`; это проверяется тестом. `diagnose-summary` теперь использует v3 по умолчанию, схема остаётся summary-v1. В рабочий API v3 не подключается. Существующие эталоны и исходные 20 примеров не изменены ради результатов модели.

## Регрессионные данные

Новые 8 искусственных переписок находятся в `evaluation/summary-regressions/inputs`. Отдельный `manual-checks.json` содержит критерии ручного просмотра, не дословные ответы и не машинную семантическую оценку. Он никогда не читается командой и не передаётся модели. Сценарии: цитата и сообщение о копировании; просьба прислать и будущие действия; отмена срока без отмены просьбы; конкретная схема с ограничениями; отсутствующая схема; напоминание и независимая просьба; подтверждённое исправление и неизвестный файл; содержательные основания вместо формальных подтверждений.

**Ранее использованные 10 holdout теперь регрессионные.** Пути `evaluation/inputs/holdout` и прежние разметки сохранены для воспроизводимости, но повторный прогон не является независимой проверкой. В `diagnose-summary` используется `--set regression`; старое --set holdout — совместимый alias с input_scope=regression. Для будущей независимой оценки нужен новый ранее не использованный набор; синтетические данные не доказывают качество на реальных клиентах.

## Команда compare-summary

Один вход обрабатывается сначала v2, затем v3, после чего берётся следующий вход. По одному вызову генерации на версию, без параллельности, повторов и repair. Канонический user JSON, JSON Schema и параметры пары одинаковы; меняется только системный промпт и его версия/хеш. Бюджет считается отдельно для каждого промпта, текст не обрезается.

Общие параметры: qwen3:8b, think=false, stream=false, keep_alive=30m, temperature=0, num_ctx=8192, num_predict/резерв=1000, shift=false, truncate=false, timeout=120s. Все проверки checksum/digest/Ollama-version/template/exact render-only/структуры/ID сохранены. Только --run разрешает HTTP и генерации. Без него — локальный план с нулём сетевых запросов. Preflight-ошибка останавливает сравнение; ошибочный уже начатый ответ сохраняется без повторной генерации, итоговый exit ненулевой. Максимум 2×N генераций, при ошибках возможно меньше.

| --set | Входов | Максимум генераций |
|---|---:|---:|
| regressions (default) | 18: 8 новых + 10 ранее использованных holdout | 36 |
| new-regressions | 8 | 16 |
| previous-holdout | 10, только регрессионный повтор | 20 |
| development | 10 | 20 |
| examples | 2 исходных примера | 4 |

Пример плана в PowerShell после подготовки отдельного venv/8B ресурсов:

```powershell
$env:BRIEFING_BUDGET_PYTHON=(Join-Path $PWD '.venv-budget/Scripts/python.exe')
$env:OLLAMA_MODEL='qwen3:8b'
go build -o bin/compare-summary.exe ./cmd/compare-summary
./bin/compare-summary.exe --set regressions
# Только ручное разрешение генераций:
# ./bin/compare-summary.exe --set regressions --run --out evaluation/reports/comparison.jsonl
```

JSONL содержит отдельную строку на версию/вход: file/input_file_sha256, pair_index/version_index, assessment_role, selection/hash, версии и хеши system/user/schema/request/render, модель/digest, бюджет, result, ошибки, токены, длительности helper/compatibility/render/HTTP/Ollama/processing. Thinking не сохраняется, невалидный result=null. Отсутствующие метрики — null. --out создаёт новый .jsonl без перезаписи, с 0600 на Unix; отчёты исключены из Git.

Сверяйте пару по pair_index, версии и одинаковому user_json_sha256. Просматривайте содержание и источники по исходной переписке и отдельным ручным критериям: тип высказывания, актуальные условия/сроки, конкретные ограничения схемы, потерянные просьбы, дубли, выдумки и неподтверждённые действия. Не требуйте дословного текста. Не меняйте эталоны для совпадения с моделью. Автоматическая структура и ключевые слова не доказывают смысловое качество. Фиксированный порядок v2→v3 может влиять на времена из-за кэша/нагрузки; это не нейтральный performance-бенчмарк. Разные длины системных промптов дают разные input_tokens при одинаковом user.

## Ручное сравнение на сервере

`tools/run-summary-comparison.sh FULL_COMMIT [SET]` создаёт отдельную копию закреплённого коммита, диагностический бинарник, venv, копию проверенных 8B ресурсов, offline-план и итоговый отчёт в `$HOME/finkoper-summary-comparison.XXXXXX`. Нужны Git, Go версии из go.mod, Python с venv/pip и сеть на этапе подготовки зависимостей. При недостаточных правах sudo используется только для чтения трёх существующих tokenizer-файлов. Никаких записей в /opt или /etc, запуска/остановки/перезапуска сервисов, изменения GPU-настроек или установки модели. При обработке зависимости не скачиваются, Ollama используется только на loopback. В финальном сообщении к изменению приведён полный bash-блок с фактическим SHA коммита.

Локально проверяются транспорт, число вызовов, изоляция ручных критериев, версии/хеши, бюджет и структура. Mock возвращает контролируемый fixture-ответ, не пытается решить содержательную задачу. Реальные генерации разработчиком не выполнялись; смысловое качество v3 ещё предстоит оценить.
