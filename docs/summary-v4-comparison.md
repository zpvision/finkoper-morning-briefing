# Диагностический summary v4: близко к исходной формулировке

`diagnostic-summary-v4` переписан с опорой на минимальное перефразирование. Разрешены отдельные предложения или строки внутри summary, без требования литературного пересказа и лимита числа предложений. Автор, действие, отрицание и время сохраняются; просьба, намерение, обещание и сообщение о выполнении не подменяются друг другом. При сомнении модель должна использовать короткую точную цитату с автором. Уточнения/отмены определяют актуальное состояние, напоминание не создаёт новую просьбу, формальное подтверждение не доказывает выполнение.

Связанный контекст раскрывает прежнюю схему с её конкретными условиями/исключениями либо явно отмечается отсутствие схемы. Старые самостоятельные темы не добавляются. Источники должны подтверждать содержание, включая использованный контекст; цитата модельной инструкции не исполняется и не становится просьбой клиента. Не применяются программные замены смысла по ключевым словам. В системном промпте нет имён, сумм, ID или готовых ответов тестовых клиентов.

Схема **summary-v1 сохранена побайтно**. V2 и v3 также сохранены побайтно в SummaryPromptV2/SummaryPromptV3; тесты закрепляют их SHA-256:

* v2: `8cc6dc4d3fad8eba8da327ecf9837aaa0213c6f978678e65c4ad105464d8ff31`;
* v3: `c8a19d2035bd5fafddaadfb4678a4a075707ddecff07713bea32135995019bd2`.

`diagnose-summary` использует v4, но рабочий API/morning-v3/topics-v1, SQLite-задания, тональность, RAG и серверные настройки не меняются. Документация интеграции рабочего API не переводится на summary. Отмеченные оператором смешанные результаты v2/v3 и около 4,8 s относятся к прежнему реальному прогону, а не к качеству/скорости v4.

## Явный выбор пары в существующей команде

Новой команды нет. `compare-summary --pair v2-v4` сравнивает v2→v4 на каждом входе. Без --pair сохраняется прежнее v2→v3. Поддерживаются только эти две пары. В отчёт добавлено поле comparison, поэтому результаты можно однозначно сгруппировать по паре и версиям.

Одинаковы user JSON, schema и параметры: qwen3:8b, think=false, temperature=0, num_ctx=8192, num_predict/резерв=1000, stream=false, keep_alive=30m, shift=false, truncate=false, timeout=120s. Различаются только системные промпты, их версии/хеши и вызванное длиной промпта количество входных токенов. Бюджет пересчитывается отдельно, обрезки нет. Все проверки ресурсов, runtime digest/версии Ollama, шаблона, exact render-only, done/length, JSON и ID сохранены.

Один вызов генерации на версию/вход, последовательно, без повторов и repair. Preflight-ошибка останавливает прогон; ошибка уже начатой генерации сохраняется, можно перейти к следующей версии/входу без повтора. Result, ошибки, токены, processing/helper/compatibility/render/HTTP/Ollama длительности и хеши сохраняются отдельно для каждого вызова. Thinking не записывается. --out создаёт новый .jsonl без перезаписи, файлы исключены из Git.

Используются **те же 18 регрессионных входов** (`--set regressions`): 8 искусственных + 10 ранее использованных holdout. Данные, разметка и ручные критерии не изменялись ради ответов модели. Повтор не является независимым holdout и не доказывает качество на реальных клиентах. Эталоны и manual-checks не читаются раннером и не передаются модели.

Из корня проекта, после установки отдельного venv/tokenizer-ресурсов:

```powershell
$env:BRIEFING_BUDGET_PYTHON=(Join-Path $PWD '.venv-budget/Scripts/python.exe')
$env:OLLAMA_MODEL='qwen3:8b'
go build -o bin/compare-summary.exe ./cmd/compare-summary
# План: 36 записей, без HTTP и генераций.
./bin/compare-summary.exe --pair v2-v4 --set regressions
# Только вручную разрешённые генерации:
# ./bin/compare-summary.exe --pair v2-v4 --set regressions --run --out evaluation/reports/v2-v4.jsonl
```

## Ручной серверный прогон

`bash tools/run-summary-comparison.sh FULL_COMMIT regressions v2-v4` включает PATH с /snap/bin, создаёт изолированные clone, бинарник, venv, копию ресурсов и отчёты в домашнем каталоге. Требуются Git, Go из go.mod (или доступный toolchain), Python с venv/pip, доступ к GitHub/PyPI при подготовке и чтение существующих 8B-ресурсов. Sudo используется только для чтения, если ресурсов не видно текущему пользователю. Скрипт не пишет в /opt или /etc, не устанавливает модель и не останавливает/перезапускает сервисы.

Сначала записывается plan.jsonl без сети, затем запускается максимум 36 последовательных генераций с сохранением comparison.jsonl. EXIT trap печатает путь отчёта и код завершения, в том числе при ошибке генерации. При раннем сбое подготовки файл может ещё отсутствовать; путь всё равно выводится после создания рабочего каталога. Повторный ручной запуск — новые генерации, автоматических повторов нет. Порядок v2→v4 и общая GPU/кэш могут влиять на длительности, это не нейтральный performance-бенчмарк.

Локальные mock-тесты проверяют только транспорт, одинаковость параметров, число/порядок вызовов, бюджет, независимую структуру/источники и обработку неполного ответа. Они не доказывают сохранение смысла. **Качество v4 до реального ручного прогона не подтверждено.**
